# B站登录增强与公开视频刷新稳定性设计

## 背景

当前 UP 主公开视频刷新依赖匿名网页投稿接口。历史失败样例为：

```text
刷新 B 站 UP 主视频失败：匿名刷新失败：投稿接口：请求 B 站 UP 主视频失败：HTTP 412
```

这说明匿名投稿接口可能被 B 站风控拦截。继续只调匿名接口会让刷新能力不稳定，用户也无法判断是 UP 主无公开视频、接口风控、登录态缺失还是请求头不完整。

本设计新增可选 B 站登录能力，让刷新链路可以使用用户主动登录后的网页会话，提高 `x/space/wbi/arc/search` 的可用性。登录只用于读取用户主动添加 UP 主的公开视频信息，不扩展为完整 B 站客户端。2026-06-11 起，UP 主公开视频刷新不再请求 `x/polymer/web-dynamic` 动态接口，也不再从动态内容补齐直播回放。

## 参考实现

参考项目：

```text
/home/niemingzhi/IdeaProjects/BiliPai
```

可借鉴内容：

- `LoginViewModel.kt`：Web 二维码登录、二维码轮询状态、登录成功后解析 `Set-Cookie`。
- `AccountSessionStore.kt`：只保存最小账号会话字段，并支持激活、退出和清理运行时 cookie。
- `ApiClient.kt`：统一网络层注入 `buvid3`、`SESSDATA`、`bili_jct`，并按接口类型设置 `User-Agent`、`Origin`、`Referer`。
- 请求失败处理边界：区分风控、登录态失效、网络错误和接口结构变化，不把外部接口失败伪装成无公开视频。

不直接复制内容：

- 不接入手机号、密码、极验验证码登录。
- 第一阶段不接 TV 登录、`access_token`、APP 签名和 token 刷新。
- 不复制 BiliPai 的完整 Android 客户端架构、播放源解析、下载、弹幕、收藏、关注和推荐能力。

## 目标

- 用户可以在“听视频”的 UP 主面板中使用 B 站 Web 二维码登录。
- 登录凭证只在 Tauri 后端或 Web 调试代理保存和使用，前端不能读取 `SESSDATA`、`bili_jct` 或完整 cookie。
- UP 主刷新优先使用登录态；未登录时保留匿名刷新能力。
- 登录态过期、被风控或接口失败时，错误信息能明确说明当前使用的是匿名刷新还是登录刷新。
- 退出登录会清理本地 B 站凭证和运行时 cookie。
- Web 环境刷新或重新进入页面后，应复用未过期登录态，避免每次重新扫码。
- 保留现有手动粘贴 B 站链接播放能力，不因登录功能失败而受影响。

## 非目标

- 不抓取真实音视频流地址。
- 不下载、缓存、转码或离线保存 B 站媒体。
- 不绕过 B 站会员、版权、地区、登录、风控或权限限制。
- 不读取用户关注列表、收藏夹、稍后再看、历史记录、推荐流或私有资源。
- 不把 B 站凭证写入前端 `localStorage`、IndexedDB、日志、错误提示、截图文本或测试快照。
- 不做多账号切换；第一阶段只维护一个当前账号。
- 不做自动后台定时刷新。

## 方案选择

### 方案 A：继续增强匿名接口

做法是继续调整匿名请求头、匿名 cookie、WBI 参数和重试顺序。

优点：

- 不引入账号凭证存储。
- 改动最小。

缺点：

- HTTP 412 仍可能频繁出现。
- 用户没有办法通过登录主动提高接口稳定性。
- 错误会继续混在“无公开视频”和“风控失败”之间。

结论：只作为兜底保留，不能作为下一阶段主方案。

### 方案 B：前端导入用户 cookie

做法是提供输入框，让用户手动粘贴 cookie。

优点：

- 实现快。
- 不需要做二维码轮询。

缺点：

- 前端会直接接触敏感凭证，泄露风险高。
- 用户体验差，复制 cookie 容易误操作。
- 很难解释 cookie 字段、过期和清理。

结论：不采用。

### 方案 C：Tauri 后端 Web 二维码登录

做法是在 Rust 后端调用 B 站 Web 二维码登录接口，前端只展示二维码和状态；登录成功后后端解析 `Set-Cookie`，保存最小会话字段，并在刷新 UP 主视频时自动注入。

优点：

- 前端不接触敏感 cookie。
- 符合当前只需要网页侧公开视频接口的需求。
- 比 TV 登录和手机号/密码登录更小、更可控。
- 后续可以扩展 secure storage 或 TV 登录，但第一阶段不用引入。

缺点：

- 需要新增登录状态机、凭证存储和退出逻辑。
- B 站 Web 登录接口仍不是本项目拥有的稳定契约。

结论：采用。

### 方案 D：Tauri 后端 TV 二维码登录

做法是接 BiliPai 的 TV 登录，保存 `access_token`、`refresh_token` 和 cookie。

优点：

- 可获得 `access_token`，适合高画质播放、APP API、token 刷新等更完整场景。

缺点：

- 当前只刷新公开视频，不需要 `access_token`。
- 需要引入 APP 签名、token 续期、过期策略和更多 B 站 API 语义。
- 容易把“听视频”功能扩展成完整 B 站客户端。

结论：不作为第一阶段；只保留为未来扩展点。

## 推荐架构

新增一个 B 站会话能力，后端负责登录、凭证保存和请求注入，前端负责展示状态和触发命令。

```text
用户点击登录
  -> 前端调用 create_bilibili_login_qr
  -> 后端请求 B 站二维码
  -> 前端展示二维码
  -> 前端轮询 poll_bilibili_login_qr
  -> 后端解析扫码状态
  -> 登录成功后后端保存最小会话字段
  -> 前端只收到账号摘要

刷新 UP 主视频
  -> fetch_bilibili_creator_videos(mid, page, pageSize, fingerprint)
  -> 后端读取 BilibiliAuthSession
  -> 构建 BilibiliRequestContext
  -> 登录态投稿接口分页
  -> 必要时匿名降级
  -> 返回公开视频列表或带模式说明的失败信息
```

## 后端设计

### 模块边界

- `bilibili_auth.rs`：二维码登录、轮询、会话解析、会话状态、退出登录。
- `bilibili_common.rs`：B 站请求共用的 `User-Agent`、cookie 注入、WBI 签名、JSON 读取和图片 URL 归一化工具。
- `bilibili_session.rs`：会话数据结构、存储读写、cookie 脱敏和过期判断。
- `bilibili_metadata.rs`：继续负责元信息和 UP 主公开视频解析，但不直接管理登录流程。
- `lib.rs`：注册新增 Tauri 命令。

如果实现时发现文件拆分会导致循环依赖，可以先把纯会话结构放进 `bilibili_metadata.rs`，但二维码登录命令必须单独形成清晰边界，避免该文件继续膨胀。

### Tauri 命令

```rust
create_bilibili_login_qr() -> BilibiliLoginQr
poll_bilibili_login_qr(qrcode_key: String) -> BilibiliLoginPollResult
get_bilibili_auth_status() -> BilibiliAuthStatus
logout_bilibili() -> ()
fetch_bilibili_creator_videos(mid, page, pageSize, fingerprint) -> BilibiliCreatorVideos
```

`fetch_bilibili_creator_videos` 使用分页入参，内部自动读取登录态。这样前端刷新调用不用携带敏感信息，也不会破坏已有测试的注入 loader 形状。

### 登录状态数据

前端可见：

```ts
interface BilibiliAuthAccount {
  avatarUrl?: string;
  mid: string;
  name: string;
}

type BilibiliLoginPollState =
  | "pending"
  | "scanned"
  | "success"
  | "expired"
  | "error";
```

后端私有：

```rust
struct BilibiliAuthSession {
    mid: Option<String>,
    name: Option<String>,
    avatar_url: Option<String>,
    sess_data: String,
    bili_jct: Option<String>,
    dede_user_id: Option<String>,
    dede_user_id_ck_md5: Option<String>,
    sid: Option<String>,
    buvid3: Option<String>,
    expires_at: Option<i64>,
    updated_at: i64,
}
```

第一阶段必须保存 `SESSDATA`。`bili_jct` 对刷新公开视频不是强依赖，但退出、后续扩展和部分接口可能需要，应在有值时保存。其他 cookie 只在登录响应里出现且非空时保存。

### 二维码登录接口

第一阶段使用 Web 二维码登录：

```text
GET https://passport.bilibili.com/x/passport-login/web/qrcode/generate
GET https://passport.bilibili.com/x/passport-login/web/qrcode/poll?qrcode_key=...
```

轮询状态按 BiliPai 经验处理：

- `0`：登录成功，解析响应头 `Set-Cookie`。
- `86101`：未扫码。
- `86090`：已扫码，等待确认。
- `86038`：二维码已过期。
- 其他状态：保留 B 站返回消息，显示为登录失败。

前端轮询间隔建议为 2 秒。组件卸载、用户关闭弹窗、登录成功或二维码过期时必须停止轮询。

### 会话存储

第一阶段采用后端私有本地存储：

- Tauri 环境文件位于 Tauri app data 目录，文件名建议为 `bilibili-session.json`。
- Web 调试和预览环境由 Vite 代理保存到用户级缓存目录，文件名为 `bilibili-web-session.json`。Linux 默认路径为 `~/.cache/sleep-companion/bilibili-web-session.json`；如果设置了 `XDG_CACHE_HOME`，则使用 `${XDG_CACHE_HOME}/sleep-companion/bilibili-web-session.json`。
- 文件只由 Rust 后端读写，前端不能通过业务 API 获取原始内容。
- Web 环境的缓存文件只由 Vite dev/preview API 读写，前端仍然只能拿到账号摘要。
- Linux 写入后尽量设置用户只读写权限。
- 退出登录时删除会话文件，并清空内存中的运行时 cookie。
- 启动 Vite dev/preview server 时预加载缓存；状态查询、UP 主刷新、直连音频解析和音频代理在使用 cookie 前都必须确认缓存已经加载。
- 如果缓存 JSON 损坏、缺少 `SESSDATA` 或已经过期，视为未登录并删除缓存文件。
- 日志和错误中只允许输出 `mid`、账号名称、是否存在 `SESSDATA`、是否存在 `bili_jct`，不能输出真实值。

后续可以把存储替换为系统凭据库或加密存储。为了不阻塞当前稳定性问题，第一阶段先保持一个小的 `BilibiliSessionStore` 抽象，避免业务请求逻辑依赖具体文件格式。

### 请求上下文

新增 `BilibiliRequestContext`，集中处理请求头和 cookie。

```text
BilibiliRequestContext
  - mode: authenticated | anonymous
  - cookie_store
  - user_agent
  - referer_for(endpoint, mid)
  - origin_for(endpoint)
```

规则：

- 已登录时，cookie_store 先放入本地会话字段，再接收接口响应下发的新 cookie。
- 未登录时，继续沿用匿名空间访问会话。
- 所有 B 站请求使用统一 `User-Agent`。
- 空间投稿接口使用 `https://space.bilibili.com/{mid}/upload/video` 作为 `Referer`。
- WBI key 请求和 WBI 签名参数构造仍走现有逻辑。

### 刷新策略

推荐顺序：

1. 如果存在登录态，先用登录态请求投稿分页接口 `x/space/wbi/arc/search`。
2. 登录态投稿接口 HTTP 412、401、403 或 B 站返回未登录类错误时，错误信息提示重新登录或稍后重试。
3. 登录态失败后再匿名降级一次，保留未登录可用时的刷新能力。
4. 没有登录态时，直接使用匿名投稿分页接口。
5. 投稿接口失败时返回明确错误，不再请求动态接口兜底。

错误信息需要包含刷新模式：

```text
登录态刷新失败：投稿接口：...。可退出后重新扫码登录，或稍后重试。
匿名刷新失败：投稿接口：...。登录 B 站后可能提高成功率。
```

## 前端设计

### Component Map

```text
VideoListeningView：页面编排、播放器状态、UP 主面板接入。
BilibiliCreatorPanel：UP 主列表、刷新按钮、视频列表、登录状态入口。
BilibiliLoginPanel：二维码登录、扫码状态、账号摘要、退出登录。
useBilibiliAuth：登录状态、二维码创建、轮询、退出登录。
bilibiliAuth.ts：Tauri 命令 loader、响应校验、状态类型。
useBilibiliCreators：刷新失败时保留错误原文，并展示登录态建议。
bilibiliCreator.ts：保持 UP 主视频 loader 入参不携带凭证。
```

`BilibiliCreatorPanel` 当前职责已经包含添加、列表、刷新、视频列表。登录 UI 要作为独立 `BilibiliLoginPanel` 嵌入，避免继续把状态机和二维码轮询堆进同一个组件。

### UI 状态

- 未登录：显示“登录 B 站提高刷新稳定性”和“扫码登录”按钮。
- 创建二维码中：显示加载状态，禁用重复点击。
- 等待扫码：显示二维码、过期提示和刷新二维码按钮。
- 已扫码待确认：显示“已扫码，请在 B 站客户端确认”。
- 已登录：显示头像、昵称、`mid`、退出登录按钮。
- 登录失败或过期：显示错误和重新获取二维码按钮。

登录区域只描述账号状态，不显示 cookie、token、接口名或复杂调试信息。

### 前端状态边界

- `useBilibiliAuth` 只管理登录相关状态，不读取或修改 UP 主列表。
- `useBilibiliCreators` 不直接知道 cookie，只根据后端刷新结果或错误更新 UI。
- 二维码轮询使用 `useEffect` 或事件启动后的显式清理，组件卸载时停止。
- 派生状态在 render 阶段计算，避免用无意义 effect 同步。
- 不在组件函数内定义子组件。

## 数据与隐私

- 敏感凭证不进入前端状态树。
- 敏感凭证不写入前端 `localStorage`、IndexedDB 或 `sessionStorage`。虽然 IndexedDB 能持久化刷新后的状态，但它可被前端 JavaScript 直接读取，不适合保存 `SESSDATA`。
- 敏感凭证不进入测试快照。
- 敏感凭证不进入日志和错误提示。
- 会话文件只保存当前功能需要的最小字段。
- 退出登录必须删除本地会话文件。
- 如果会话解析失败或缺少 `SESSDATA`，视为未登录，不写入半成品会话。

## 破坏性更新说明

本设计不需要破坏性更新：

- 不删除当前匿名刷新能力。
- 不改变已保存 UP 主列表的数据结构。
- 不改变现有 B 站链接解析和官方 iframe 播放方式。
- 不要求迁移已有用户数据。

用户可见变化：

- UP 主面板新增 B 站登录区域。
- 刷新错误会区分登录态和匿名模式。
- 退出登录只影响 B 站 UP 主刷新增强，不影响本地音频、听书、手动 B 站链接播放和全局播放控制。

## 验收标准

- 未登录时，现有匿名刷新逻辑仍可运行。
- 用户可以创建登录二维码，并看到等待扫码、已扫码、成功、过期和失败状态。
- 登录成功后，前端只能看到账号摘要，不能读取 cookie。
- Web 环境登录成功后，刷新页面或重新打开同一个 dev/preview server 时能复用未过期会话，不需要重复扫码。
- 登录成功后，刷新 UP 主视频时后端请求会携带登录态 cookie。
- 退出登录后，本地会话文件被删除，后续刷新回到匿名模式。
- 登录态失效时，刷新错误明确提示重新登录。
- `fetch_bilibili_creator_videos` 入参不新增 cookie 字段。
- TypeScript 测试覆盖 `bilibiliAuth.ts` 响应校验和 hook 状态转换。
- Rust 测试覆盖 `Set-Cookie` 解析、登录轮询状态解析、cookie 脱敏、请求上下文 cookie 注入。
- 完成实现后必须运行：

```bash
pnpm run check
```

## 遗留风险

- B 站 Web 登录和网页接口仍可能变化，不是稳定公开契约。
- 本地文件存储不等同于系统凭据库，后续如果提高隐私等级，应替换为系统安全存储。
- Android 端 Tauri app data 权限和二维码显示需要真机验证；未配置 Android SDK 或 `adb` 时不能声称真机通过。
- 登录只能提高公开视频刷新成功率，不能保证所有 UP 主、所有网络环境和所有接口永远可用。
