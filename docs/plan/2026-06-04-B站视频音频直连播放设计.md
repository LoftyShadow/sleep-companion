# B 站视频音频直连播放设计

## 背景

当前“听视频”模式依赖 B 站官方 `iframe` 播放器。直播 iframe 可通过 `postMessage` 控制播放和音量，但普通视频 iframe 是跨域播放器，外层页面不能稳定控制播放、暂停和音量。用户明确要求改成直连模式，不再使用 iframe。

登录增强已经提供 B 站登录态保存和 Web/Tauri 双环境代理能力，因此可以在后端侧使用登录态请求 B 站播放地址，再把可播放音频通过本地代理暴露给前端播放器。

## 目标

- 普通 `BV` 和 `av` 视频使用音频直连模式播放，不渲染 B 站官方 iframe。
- 前端使用自己的 `<audio>` 控制播放、暂停、音量和状态。
- 在直连响应可提供视频轨时，页面提供可展开/隐藏的视频画面，默认隐藏。
- B 站 Cookie、`SESSDATA`、`bili_jct` 等登录凭证只留在 Tauri 后端或 Vite 开发代理内，不进入前端状态、DOM、日志或测试断言。
- Web 开发/预览环境和 Tauri 桌面环境使用同一套前端接口。
- 全局停止和模块播放控制继续可用。

## 非目标

- 第一版不支持 `ep` 番剧直连；页面要给出明确提示。
- 第一版不支持直播直连；直播不再使用 iframe，页面提示当前直连模式暂不支持直播。
- 不实现弹幕、清晰度选择、分 P 切换、字幕、播放速度、进度持久化。
- 不把 B 站真实音频 URL 直接暴露成需要前端带 Cookie 的跨域请求。

## 方案选择

### 方案 A：继续 iframe 并尝试外部控制

优点是改动小。缺点是普通视频跨域 iframe 没有稳定公开控制协议，登录也不能改变浏览器跨域限制，播放、暂停和音量仍不可靠。

结论：不采用。

### 方案 B：后端解析音频流，前端 `<audio>` 播放

后端用登录态请求 `view` 和 `playurl`，从 DASH 音频轨中选一个音频地址，再提供本地代理 URL。前端只播放本地代理 URL，并用 `<audio>` 自有 API 控制。

优点是控制权在应用自己手里，能统一播放、暂停和音量。缺点是依赖 B 站播放地址接口，接口失败时只能给出错误。

结论：采用。

### 方案 C：在方案 B 上补充可选视频轨画面

B 站 DASH 通常把音频轨和视频轨分开返回。为了不重新引入 iframe，也不在第一版引入复杂的 MSE/DASH 播放内核，主播放仍由 `<audio>` 承担；当 `playurl` 返回可用视频轨时，前端额外渲染一个静音 `<video>` 作为画面预览，并跟随主音频播放/暂停。视频区域默认隐藏，用户展开后才挂载视频元素并请求视频流。

优点是保留当前稳定的音频控制链路，同时恢复可选视频画面。缺点是音画同步只覆盖播放/暂停和初始时间对齐，不提供完整进度条、拖动和多轨合成能力。

结论：本轮采用，作为直连模式的轻量视频画面。

## 架构

### 前端

- `bilibiliVideo.ts` 继续负责解析用户输入为 `BilibiliReference`。
- 新增 `bilibiliDirectAudio.ts`：
  - 定义 `BilibiliDirectAudioSource`。
  - 提供 Tauri client 和 Web client。
  - 在响应中允许携带可选 `videoUrl`、`videoCodecs`、`videoMimeType` 等视频轨摘要。
  - 运行时根据 `hasTauriInvoke()` 选择通道。
- 新增 `useBilibiliDirectAudioPlayer.ts`：
  - 持有 `<audio>` 引用、加载状态、播放状态、错误、音量。
  - 负责载入直连音频、播放、暂停、停止和音量同步。
- 新增 `BilibiliVideoPlaybackPanel.tsx`：
  - 展示默认隐藏的视频画面区域。
  - 展开后挂载静音 `<video>`，跟随主 `<audio>` 播放状态。
  - 保留直连媒体源摘要信息。
- `VideoListeningView.tsx`：
  - 不再渲染普通视频 iframe。
  - 对 `BV/av` 调用直连音频 loader。
  - 对 `ep/live` 显示“当前直连模式暂不支持”。

### Tauri 后端

- 新增 `bilibili_direct_audio.rs`：
  - `resolve_bilibili_direct_audio` 根据 `bvid/aid` 获取 `cid`。
  - 请求 B 站 `playurl` 获取 DASH 音频轨。
  - 选择带宽最高的可用音频轨。
  - 尝试选择一个浏览器兼容性优先的视频轨，优先 `avc1`，否则使用可用最高带宽视频轨。
  - 返回音频 URL、可选视频 URL 和摘要信息，不返回 Cookie 或登录凭证。
- 本地代理第一版使用 Tauri 自定义协议或命令暴露可播放 URL 的难度较高。为保持第一版可落地，Tauri 先返回带签名参数的真实音频和视频 URL，但前端不附带 Cookie；如果 B 站防盗链阻止桌面端播放，后续再补 Tauri 流代理。

### Web/Vite 代理

- Vite 增加：
  - `GET /api/bilibili/direct-audio?...` 返回前端可播放的本地代理 URL。
  - `GET /api/bilibili/media-proxy?...` 代理 B 站音频和视频流，设置必要 `Referer`、`User-Agent`、`Cookie` 和 Range 头。
  - `GET /api/bilibili/audio-proxy?...` 暂时保留为旧测试和旧客户端兼容入口。
- Web 前端只播放 `/api/bilibili/media-proxy?...`，不直接访问 B 站真实媒体 URL。

## 数据流

1. 用户输入 `BV` 或 `av`。
2. 前端解析为 `BilibiliReference`。
3. 前端请求直连音频 source。
4. 后端读取可用登录态。
5. 后端请求 `view` 获取 `aid`、`bvid`、`cid`、标题、封面。
6. 后端请求 `playurl` 获取 DASH 音频轨，并尝试读取 DASH 视频轨。
7. 后端返回本地可播放音频 URL 和可选视频 URL。
8. 前端 `<audio>` 设置 `src`，用户可播放、暂停和调音量。
9. 视频画面默认隐藏；用户展开后，前端静音 `<video>` 设置视频轨 `src` 并跟随音频播放状态。

## 失败路径

- 未登录或登录态失效：仍尝试匿名请求；失败时提示登录后重试。
- B 站返回风控或无音频轨：显示“直连音频不可用”，不回退 iframe。
- B 站返回音频轨但无视频轨：保持音频播放可用，视频展开按钮不可用或显示画面不可用。
- `ep/live`：提示暂不支持直连。
- 音频播放失败：保留封面和标题，显示浏览器播放失败信息。
- 视频轨播放失败：不影响主音频播放，视频区域显示画面暂不可用。

## 验收标准

- 普通 `BV/av` 载入后页面不出现 B 站官方 iframe。
- 播放按钮控制 `<audio>` 播放和暂停。
- 音量滑块对普通视频可用，并同步到 `<audio>.volume`。
- 视频画面默认隐藏，不在载入后自动显示。
- 响应包含视频轨时，用户可展开视频画面并再次隐藏。
- 全局停止能清空当前直连音频。
- Web 登录态不向前端暴露 `SESSDATA`、`bili_jct` 等凭证。
- 必须通过 `pnpm run check`。

## 风险

- B 站播放地址、防盗链和风控策略可能变化。
- Tauri 桌面第一版如果直接播放真实 B 站音频或视频 URL，可能受 Referer 限制；必要时后续补 Rust 流代理。
- 当前视频画面是轻量静音视频轨预览，不等价于完整 DASH 音视频合成播放器。
- `ep`、分 P、多音轨和直播直连需要后续单独设计。
