# 代码结构深度拆分优化设计

## 背景

本次重构来自 2026-06-08 的只读代码审查。审查发现当前代码已经具备完整功能，但部分模块职责继续叠加，后续扩展 B 站直连播放、UP 主刷新、声音库和 Android 原生播放时，维护成本和回归风险会明显上升。

主要热点：

- `BilibiliVideoPlaybackPanel.tsx` 同时维护视频轨选择、视频源回退、进度条、章节、视频元素播放控制和媒体源详情。
- `VideoListeningView.tsx` 同时维护 B 站输入解析、直连音频加载、收藏同步、剪贴板、全局播放控制和页面 JSX。
- `bilibili_metadata.rs` 与 `bilibili_direct_audio.rs` 重复实现 B 站请求、WBI key、状态码校验和 `reqwest::Client` 构造。
- `SoundGrid.tsx` 对声音卡片整体渲染缺少单卡片边界，音量变化会扩大 React render 范围。
- Android `NativeAudioPlayer` 每次首次播放声音都动态查找 raw 资源 ID，资源名错误也只在运行时暴露。

## 目标

- 拆分 `BilibiliVideoPlaybackPanel`，让视频预览状态机、进度/章节 UI、媒体源详情和纯格式化逻辑各有边界。
- 拆分 `VideoListeningView`，让页面组件只做编排，把业务状态和动作下沉到 controller hook。
- 统一 Rust B 站 HTTP/WBI 基础设施，减少请求策略和错误处理漂移。
- 给声音卡片建立可 memo 的叶子组件边界，降低声音库局部状态变化的重渲染范围。
- 给 Android raw 资源 ID 增加缓存，减少重复反射式查找。
- 保持用户可见行为、接口、数据结构和测试语义不变。

## 非目标

- 不改变 B 站功能范围，不新增番剧或直播直连播放。
- 不改变音频文件目录、Android raw 文件命名或内置声音清单语义。
- 不重做界面视觉设计，不改现有 CSS className 语义。
- 不引入新的前端状态库、虚拟列表库或 Rust HTTP 抽象框架。
- 不改 Android 后台播放、锁屏控制或通知栏控制。

## 组件地图

```text
VideoListeningView：页面编排，连接 controller、输入面板、播放面板、视频预览、收藏和 UP 主区块。

VideoLinkPanel：链接输入、粘贴、载入、来源摘要。
VideoNowPanel：封面、当前播放状态、音频元素、播放按钮、音量控制。
BilibiliVideoPlaybackPanel：视频预览区块编排。
useBilibiliVideoPreview：视频轨选择、源回退、展开/收起、预览失败状态和视频元素同步。
bilibiliVideoPlaybackUtils：格式化、进度计算、章节定位、视频轨派生、fallback 动作计算。
VideoProgressControls：播放进度和章节选择。
VideoSourceDetails：直连媒体源详情。
SoundGrid：声音网格编排。
SoundCard：单个声音卡片，可 memo。
```

## Rust 边界

```text
bilibili_common.rs：通用请求工具、B 站 client 构造、cookie header、WBI key、状态码校验、JSON 读取工具。
bilibili_direct_audio.rs：直连音频流程和 DASH 解析。
bilibili_metadata.rs：元信息和 UP 主投稿视频解析/编排。
bilibili_auth.rs：登录、二维码、cookie 导入和网页登录同步。
```

Rust 重构只下沉共用基础设施，不改变 Tauri 命令签名。

## 方案取舍

### 前端拆分

采用“controller hook + 展示组件 + pure utils”的方案。

理由：

- 当前问题来自单组件职责过多，不需要引入全局状态库。
- controller hook 可以集中副作用和外部控制请求，展示组件保持纯 props。
- pure utils 能单独被测试或被 hook 使用，不依赖 DOM。

不采用“完全按每个 UI 小块拆组件”的方案，因为只有一次使用且没有独立状态语义的 DOM 片段会增加目录噪音。

### Rust 请求层

采用在 `bilibili_common.rs` 增加小型 helper 的方案。

理由：

- 现有模块已经共享 cookie、WBI 和 JSON 读取工具，继续放在 common 最小。
- 不引入 trait 或大型 client 类型，避免为当前需求制造过度抽象。
- 保留各业务模块自己的错误上下文，避免错误信息变泛。

### 声音网格

采用 `memo(SoundCard)` 和稳定 callback 的方案。

理由：

- 当前声音数量已经较多，但列表仍按分类展示，暂不需要引入虚拟列表。
- 单卡片边界能直接减少音量变化、播放状态变化时的 render 扩散。
- 不改变 DOM 结构和 CSS 选择器，回归风险低。

## 破坏性更新说明

本次不设计破坏性更新。

- 前端组件 props 对外导出保持当前语义。
- Tauri 命令名和参数不变。
- Android 插件命令不变。
- 音频资源路径和 raw 资源名不变。

## 验收标准

- `BilibiliVideoPlaybackPanel.tsx` 不再直接包含视频 fallback 状态机和媒体源详情大段 JSX。
- `VideoListeningView.tsx` 不再直接包含主要业务加载流程和外部播放控制副作用。
- B 站 Rust 模块的 WBI key 拉取、client 构造和 JSON 请求基础逻辑只保留一份实现。
- 声音卡片拆成可 memo 的叶子组件，父级只传递单卡片实际需要的 primitive 状态和稳定动作。
- Android raw 资源 ID 通过缓存复用，缺失资源仍返回原有错误语义。
- 现有测试继续覆盖：
  - 视频预览备选源回退。
  - 视频无法渲染时切回音频。
  - 画质切换。
  - 进度和章节跳转。
  - B 站 Rust 解析。
  - 声音播放和 Android 原生播放适配。
- 必须通过仓库质量门禁：

```bash
rtk pnpm run check
```

## 风险

- 视频预览 hook 拆分后 dependency 变化可能导致定时回退提前或延后触发，必须用现有假定时器测试保护。
- `VideoListeningView` controller 拆分后，悬浮播放请求 ID 和全局停止请求 ID 不能重复消费。
- Rust helper 下沉时，业务模块的 Referer、Origin 和 cookie 更新顺序必须保持一致。
- `memo(SoundCard)` 只有在 callback 和 props 稳定时才有收益，不能引入新的 inline object props。
