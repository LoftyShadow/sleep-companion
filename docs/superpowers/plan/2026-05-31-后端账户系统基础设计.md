# 后端账户系统基础设计

## 背景

本项目后续需要保存用户数据，并支持 AI 故事、AI ASMR、生成额度、生成历史和跨设备同步。经过方案讨论，第一版不接入 Supabase Auth，也不做手机号、第三方 OAuth 或 MFA，先采用独立服务器端的邮箱密码账户体系。

后端作为独立云端服务运行，不放入 `src-tauri`。Tauri/React 继续作为客户端，通过 HTTP API 调用后端。

## 目标

- 在当前仓库中新增独立 `backend/` 服务。
- 使用 `Axum + SeaORM + PostgreSQL` 作为第一版后端基础栈。
- 新增根 `Cargo.toml`，把 `backend` 和 `src-tauri` 纳入同一个 Rust workspace。
- 建立账户系统的数据模型、配置体系、响应约定和健康检查接口。
- 保持业务用户主表为 `app_users`，后续业务关系通过逻辑外键引用 `app_users.id`。

## 非目标

- 基础阶段不实现完整注册、刷新 token、邮箱验证和找回密码接口。
- 第一版不实现邮箱验证流程。
- 本阶段不接入真实邮件服务。
- 本阶段不接入 AI 生成供应商。
- 第一版不实现 AI 故事和 AI ASMR 生成。
- 基础阶段不实现前端登录 UI。
- 本阶段不引入 Redis、独立任务队列或微服务拆分。

## 当前状态说明

本设计记录后端基础阶段的架构约束。后续已经在本仓库实现邮箱密码登录、邮箱密码注册和前端“我的”入口；这些能力继续沿用本文定义的响应 envelope、短期 access JWT、数据库持久化 opaque refresh token、逻辑外键和审计字段约束。

截至当前实现，仍未提供 refresh token 轮换、退出登录、会话恢复、邮箱验证、找回密码、真实邮件发送、第三方登录、手机号登录、AI 故事生成和 AI ASMR 生成功能。

## 技术选型

### 后端框架

后端采用 `Axum`。它与 Rust 异步生态、`tower` 中间件和 `tower-http` 观测能力配合自然，适合从单体服务起步。

### 数据访问

数据库访问目标方案改为 `SeaORM`。后端需要较多账户、用户数据、AI 任务、生成资产和后续管理类 CRUD，使用 SeaORM 可以减少重复仓储代码，并让实体、迁移和业务模型有更统一的组织方式。

采用 SeaORM 后仍保留以下约束：

- ID 由应用层 Snowflake 风格 `IdGenerator` 生成，不依赖数据库自增。
- 数据库默认不声明外键，SeaORM entity 中只表达字段和查询关系，不依赖数据库级外键约束。
- 复杂查询、JSONB 查询、部分索引和巡检 SQL 可以继续使用原生 SQL 或 SeaQuery，不强行通过 ORM 表达。
- 业务代码不直接散落 ActiveModel 操作，仍按 `handler -> service -> repository` 或等价分层组织。

当前基础骨架已经切换为 SeaORM 连接层，并把数据库版本管理拆到独立 `backend-migration` crate。后端服务启动时只建立数据库连接和提供 readiness 检查，不自动执行 migration；migration 由本地开发或部署流程显式执行。

### 数据库

数据库采用 PostgreSQL。本地开发可以直接使用本机 PostgreSQL，也可以通过现有 Docker Compose 启动后端服务；PostgreSQL 仍由本机或外部托管数据库提供。数据库 migration 由 `sea-orm-migration` 管理，不强制要求后端启动时自动执行。

### 数据库版本管理

数据库版本管理采用 `sea-orm-migration`，与 SeaORM 数据访问层保持一致。

迁移原则：

- migration 必须进入版本控制。
- migration 文件只向前追加，不修改已经在共享环境执行过的 migration。
- 本地开发允许手动执行 migration。
- 生产环境由部署流程在启动后端服务前单独执行 migration。
- 生产环境不允许多个后端实例在启动时自动并发执行 migration。
- 需要回滚时优先通过新的向前 migration 修复；只有开发环境允许使用 `down`、`fresh`、`reset` 这类破坏性命令。

推荐命令形态：

```bash
cargo run -p backend-migration -- up
cargo run -p backend-migration -- status
```

第一版已经采用独立 migration crate，目录结构为：

```text
backend/
backend-migration/
```

实体当前放在 `backend/src/entity/` 内，后续只有在实体规模显著增长、多个服务复用实体，或生成实体代码需要独立边界时，再考虑拆出 `backend-entity` crate。

### 配置管理

后端采用 `config` crate 加载分层 TOML 配置，而不是只依赖 `.env`。加载顺序为：

```text
1. 解析当前配置环境：
   APP_ENV
   -> backend/config/local.toml 中的 app.env
   -> backend/config/environment.toml 中的 app.env
   -> local

2. 加载运行配置：
   backend/config/default.toml
   + 所选环境 TOML
   + backend/config/local.toml
   + APP_ 环境变量覆盖
```

`environment.toml` 是可提交的环境选择入口，默认配置为：

```toml
[app]
env = "local"
```

`local.toml` 用于本机私有配置并加入 `.gitignore`，仓库只提交 `local.toml.example`。本机如需覆盖默认环境，可以在 `local.toml` 中写入 `[app].env`；临时启动或部署场景仍可用 `APP_ENV` 覆盖。生产环境的数据库连接串、JWT secret 等敏感信息必须通过环境变量或部署平台注入。

数据库配置采用结构化字段优先，便于本地开发和 RustRover 中查看：

```toml
[database]
host = "localhost"
port = 5432
database = "sleep_companion_dev"
username = "postgres"
password = "postgres"
ssl_mode = "disable"
max_connections = 10
```

后端服务同时保留可选的完整连接串覆盖：

```toml
[database]
url = "postgres://postgres:postgres@localhost:5432/sleep_companion_dev"
```

规则是：如果 `database.url` 存在且非空，优先使用完整连接串；否则用 `host`、`port`、`database`、`username`、`password`、`ssl_mode` 拼接 PostgreSQL 连接串。这样本地配置接近 Spring 风格，生产和云平台仍可直接注入完整连接串。

Docker Compose 部署时仍然遵循上述配置顺序。Compose 中的 `APP_DATABASE__URL`、`APP_AUTH__JWT_SECRET` 等环境变量只是覆盖 TOML 中的敏感配置项，不替代 TOML 配置体系。普通非敏感默认值继续放在 `backend/config/*.toml` 中。

`backend-migration` 默认复用后端服务的 TOML 配置加载逻辑，并从 `[database]` 结构化字段或 `database.url` 推导连接串。本地执行 migration 时不需要重复手写连接串；部署或临时覆盖时仍保留标准 `DATABASE_URL` 环境变量，并让它优先于 TOML 配置。

### 日志与观测

第一版采用以下日志组合：

```text
tracing
tracing-subscriber
tower-http TraceLayer
```

开发环境同时输出控制台日志和本地日志文件，便于在问题发生后直接回看：

```text
backend/logs/backend-dev.log
```

生产环境默认输出 JSON 格式到 stdout，由 Docker、systemd 或后续日志平台采集。第一版不直接接入 OpenTelemetry，但代码中的 span 和 event 设计不得阻碍后续增加 `tracing-opentelemetry`。

配置结构：

```toml
[logging]
level = "info"
format = "pretty"
write_to_file = true
file_path = "backend/logs/backend-dev.log"
```

生产环境覆盖为：

```toml
[logging]
level = "info"
format = "json"
write_to_file = false
```

日志字段应逐步统一：

```text
timestamp
level
target
message
request_id
method
uri
status
latency_ms
app_user_id
error_code
```

敏感信息不得进入日志：

```text
password
access token
refresh token
邮箱验证 token
密码重置 token
完整 Authorization header
供应商密钥
完整 AI prompt
```

完整 AI prompt 如果需要排障，只记录 hash、长度和安全摘要。

API envelope 中的 `requestId` 和响应 header `x-request-id` 必须保持一致。当前健康检查、登录和注册接口已经通过 request-id middleware 生成或透传 `x-request-id`，并写入成功响应 envelope；Auth 业务错误也会把 request id 贯穿到错误响应中。错误响应中的兜底 `req_unavailable` 只用于未显式传入 request id 的异常路径。tracing span 中的 `request_id` 字段会在后续日志字段统一时补齐。

### 接口文档

第一版接口文档采用 `utoipa + utoipa-swagger-ui`。

目标：

- 由后端代码生成 OpenAPI 文档。
- 开发环境提供可视化接口页面，便于前端和调试使用。
- 后续可以基于 OpenAPI JSON 生成 TypeScript client 或接口类型。

推荐暴露路径：

```text
GET /api-docs/openapi.json
GET /swagger-ui
```

配置结构：

```toml
[openapi]
enabled = true
swagger_ui_enabled = true
```

生产环境默认关闭 Swagger UI：

```toml
[openapi]
enabled = false
swagger_ui_enabled = false
```

如果生产环境需要保留 OpenAPI JSON，必须通过内网、鉴权或部署层访问控制保护，不能无保护公开调试接口说明。

接口文档规则：

- 请求 DTO、响应 DTO 和错误码需要进入 OpenAPI schema。
- 统一响应 envelope 必须体现在 OpenAPI 中。
- Auth 接口必须标注可能返回的业务错误码，例如 `auth.invalid_credentials`、`auth.email_not_verified`。
- 不在 OpenAPI 示例中放真实 token、真实邮箱、供应商密钥或生产域名。

### CORS

当前 CORS 已经改为配置驱动。本地开发和测试配置保持宽松，服务于 Tauri、Web、本地开发和调试便利性；生产配置关闭宽松模式，通过 `allowed_origins` 显式声明允许来源。

如果生产环境开放公网并承载真实用户数据，必须配置真实前端域名，并重新评估凭证策略和反向代理边界。

### 定时任务

第一版定时任务采用 `tokio-cron-scheduler`，只用于轻量维护任务，不用于执行 AI 生成。

适合放入定时任务的内容：

```text
清理过期 email_verification_tokens
清理过期 password_reset_tokens
清理过期或已吊销 refresh_sessions
巡检逻辑外键孤儿数据
后续汇总轻量统计
```

不适合放入定时任务的内容：

```text
AI 故事生成
AI ASMR 生成
长时间音频处理
需要失败重试和成本记录的用户任务
```

AI 生成属于后台任务队列问题，后续应通过 `generation_jobs` 表和 worker 处理；当任务量上升后再评估 `apalis` 或其他 Postgres/Redis backed job queue。

配置结构：

```toml
[scheduler]
enabled = true

[scheduler.jobs.cleanup_expired_tokens]
enabled = true
cron = "0 0/30 * * * *"
```

多实例部署时，进程内 scheduler 会在每个开启它的实例中运行。生产环境必须保证同一类维护任务只在一个实例启用，或后续通过 PostgreSQL advisory lock / job table 抢占机制保证单次执行。

## ID 策略

后端不使用 UUID 作为默认主键。第一版采用应用层生成的 Snowflake 风格分布式 `bigint` ID。

数据库字段：

```sql
id bigint primary key
```

Rust 内部可以用 `i64` 或后续封装的新类型承载。前端 JSON 不直接传数字 ID，统一传字符串，避免 JavaScript 对 64 位整数丢精度：

```json
{
  "id": "739182738912312320"
}
```

ID 生成器通过配置指定 worker id：

```toml
[id_generator]
worker_id = 1
```

每个后端实例必须使用不同 `worker_id`。第一版单实例使用 `1`，多实例部署时由部署环境注入不同值。不要从 IP、MAC、hostname 自动推导 worker id，避免容器和迁移场景下产生不可控冲突。

业务代码不直接依赖第三方 Snowflake crate。当前已经定义项目内 `IdGenerator` 抽象，并由 `SnowflakeIdGenerator` 实现，便于未来替换实现。

## 数据库通用字段

普通业务表采用以下通用字段：

```sql
id bigint primary key,

created_at timestamptz not null default now(),
updated_at timestamptz not null default now(),
deleted_at timestamptz,

created_by bigint,
updated_by bigint,

metadata jsonb not null default '{}'::jsonb
```

`created_by` 和 `updated_by` 是逻辑外键，语义上指向 `app_users.id`，但数据库不声明外键约束。业务归属字段不作为通用字段强制加入；如果某个表需要表达资源归属，使用该表自己的业务字段，例如 `owner_id`，同样采用逻辑外键。

`metadata` 仅用于非核心、低频查询、供应商响应摘要、实验字段和客户端环境快照。不得放入密码、token、密钥、核心状态、需要唯一约束或频繁查询排序的字段。

本项目默认不声明数据库外键，引用关系通过应用层约束和后续数据巡检维护。

### Entity 复用边界

后端不采用 Java/JPA 风格的 `BaseEntity` 继承，也不使用 PostgreSQL table inheritance。SeaORM entity 必须保持数据库列平铺在各自的 `Model` 上，避免把真实列隐藏在嵌套结构中。

通用字段通过三层方式保持一致：

```text
数据库层：migration 显式声明通用字段。
Entity 层：每张表的 SeaORM Model 平铺声明字段。
行为层：通过 trait、helper 和 repository 约定复用通用行为。
```

当前 entity 层提供 `HasAuditFields` trait，用于统一读取以下审计和软删除字段：

```text
created_at
updated_at
deleted_at
created_by
updated_by
metadata
```

`HasAuditFields` 只负责通用字段的读取行为和基础软删除判断，不改变数据库 schema，也不替代 SeaORM entity 的字段声明。后续注册、登录和业务表 repository 实现时，应继续把软删除过滤、审计字段填充和 `metadata` 使用边界放在 repository/service 层统一处理。

## 账户模型

后端自己维护业务用户表：

```text
app_users
password_credentials
email_verification_tokens
password_reset_tokens
refresh_sessions
```

账户相关表也采用 `bigint` ID 和逻辑外键，不声明数据库外键约束。

## 安全约束

- 密码必须使用 `Argon2id` 或同级方案哈希保存。
- 第一版密码最小长度为 6 位。
- 邮箱验证 token 和密码重置 token 只保存哈希值。
- 第一版只对登录接口做组合限流。
- 找回密码和登录失败信息后续必须避免泄露邮箱是否存在。
- 生产环境不得打印完整验证链接、重置链接或 token 原文。
- refresh session 必须可吊销，修改密码后应能失效旧 session。

## 限流策略

第一版只实现登录限流，采用组合限流策略，至少同时考虑：

```text
IP
邮箱
IP + 邮箱
```

注册接口当前不单独限流，登录限流继续只保护登录失败路径。后续如果开放真实公网注册、邮箱验证、忘记密码或 AI 生成接口，必须按接口风险补充独立限流策略。

登录限流命中时返回统一错误 envelope，业务错误码建议为：

```text
auth.rate_limited
```

错误响应不得暴露该邮箱是否存在。

## 部署形态

第一版按 Docker Compose 部署后端服务，但 Compose 文件不内置 PostgreSQL。PostgreSQL 由外部托管数据库或用户已有数据库提供，通过配置注入连接串。

部署边界：

- Compose 管理后端服务进程。
- PostgreSQL 不作为 Compose 内部服务提交。
- migration 由部署流程在启动后端前单独执行。
- 配置通过 TOML 文件和环境变量注入；环境变量用于覆盖生产敏感项，不替代 TOML 分层配置。
- 开发环境可以继续直接连接本机或外部 PostgreSQL。

## 邮件发送边界

后端预留 `MailSender` 抽象，只定义当前账户体系明确需要的两类邮件：

```text
发送邮箱验证邮件
发送密码重置邮件
```

第一阶段使用 `NoopMailSender`，不请求外部邮件服务，不输出验证 token 或重置 token 原文。后续接入 Resend、Postmark 或 SES 时，只新增 `MailSender` 实现，不让注册和找回密码业务直接依赖供应商 SDK。

## Token 策略

登录态采用短期 access JWT 加数据库持久化 opaque refresh token。

```text
access token
  - 格式：JWT
  - 默认有效期：15 分钟
  - 用途：客户端访问普通业务 API
  - 存储：客户端内存或平台安全存储，后续由客户端实现细化

refresh token
  - 格式：高熵随机 opaque token
  - 默认有效期：30 天
  - 服务端存储：只保存 token hash
  - 用途：换取新的 access token，并轮换 refresh session
  - 管理：支持退出登录、按设备吊销、改密码后批量失效
```

不采用长期 JWT 作为唯一登录凭证。长期 JWT 难以服务端主动吊销，不适合后续的设备管理、改密码失效、账号封禁和异常会话处理。

## 当前接口

当前已经提供：

```text
GET /healthz
GET /readyz
POST /api/auth/login
POST /api/auth/register
```

`/healthz` 用于进程存活检查，不访问数据库。`/readyz` 用于数据库连接检查。
`/api/auth/login` 用于邮箱密码登录，返回 access token 和 refresh token。
`/api/auth/register` 用于邮箱密码注册，成功后直接返回与登录一致的 token 和用户信息。

## API 响应约定

前后端统一使用响应 envelope，但不废弃 HTTP status。

成功响应：

```json
{
  "code": "ok",
  "message": "ok",
  "data": {},
  "requestId": "req_..."
}
```

错误响应：

```json
{
  "code": "auth.invalid_credentials",
  "message": "邮箱或密码错误",
  "data": null,
  "requestId": "req_...",
  "details": {}
}
```

规则：

- `2xx` 表示协议层成功，`code` 默认为 `ok`。
- `4xx` 表示客户端问题，例如未登录、参数错误、额度不足。
- `5xx` 表示服务端问题。
- 前端业务判断优先使用 `code`，不要依赖中文 `message`。
- `message` 用中文，面向用户或接近用户可见。
- `requestId` 用于串联前端错误、后端日志和后续排障。
- `details` 只放字段错误等安全信息，不放密码、token、数据库错误原文或供应商密钥。

分页响应放在 `data` 内：

```json
{
  "code": "ok",
  "message": "ok",
  "data": {
    "items": [],
    "page": {
      "limit": 20,
      "nextCursor": "..."
    }
  },
  "requestId": "req_..."
}
```
