# 全仓规模化优化设计

## 背景

本次优化面向整个 `sleep-companion` 仓库，而不是单一功能文档。当前项目已经形成 React 前端、Tauri 2 桌面壳、Rust 原生命令和 Android 生成工程的多端结构。功能模块按 `features` 拆分，整体边界清楚，但随着白噪音、ASMR、自定义音频、听书、听视频、全局定时停止等能力叠加，部分文件开始承担过多职责。

当前工作区已有未提交改动，集中在系统 TTS 听书文档、`src-tauri/Cargo.toml`、`src/features/audiobook/*`。本次优化必须保护这些改动，只做可合并、可验证、低风险的增量调整。

## 目标

- 降低页面壳和核心 hook 的职责密度，让后续功能继续增长时更容易维护。
- 优先处理已经超过或接近 250 行的文件，以及同时承担状态、副作用、UI 编排的文件。
- 不改变现有用户可见行为，不新增文档外能力。
- 每个优化点都要能被现有测试、类型检查、lint 或构建验证。

## 当前规模信号

- `src/features/mixer/SoundMixerView.css` 约 470 行，是当前最大的样式文件，后续适合按面板或组件边界拆分。
- `src/features/audiobook/epubImport.ts` 约 389 行，承担 EPUB 解析、HTML 文本提取、章节组织等多项职责。
- `src/features/player/useSoundMixer.ts` 约 348 行，混合播放命令、音量状态、预设应用、错误处理和开发日志。
- `src/features/audiobook/useAudiobookPlayer.ts` 约 328 行，混合 TTS 音色加载、播放状态机、章节跳转和语言推断。
- `src/features/appMode/AppWorkspace.tsx` 虽然只有约 142 行，但同时负责模式切换、运行时播放器创建、全局定时停止和三种业务视图编排，是后续膨胀入口。

## 方案

### 已采纳方案：先拆页面壳副作用

先把 `AppWorkspace` 中与页面壳编排无关的副作用拆出：

- `useRuntimePlayer` 负责在未注入测试播放器时创建和销毁运行时播放器。
- `useGlobalSleepTimer` 负责定时器状态、倒计时和全局停止请求编号。

理由：

- 行为面小，现有 `AppWorkspace` 测试已经覆盖定时停止、模式切换和播放器注入。
- 可降低 `AppWorkspace` 的状态数量，让它只保留应用模式和懒加载视图开关。
- 不触碰当前已有改动最多的 audiobook 文件，降低覆盖风险。

### 后续候选方案

- `useSoundMixer.ts`：把纯函数和开发日志拆到同目录工具文件，或引入轻量命令 helper；不建议现在引入 reducer，避免为已有简单状态制造额外抽象。
- `SoundMixerView.css`：按 `MixerHeader`、`PlayerSummary`、`PresetGroups`、`SoundGrid`、`CustomAudioPanel` 的现有组件边界移动样式，减少全局 feature 样式文件体积。
- `epubImport.ts`：拆分为 EPUB 容器读取、HTML 文本提取、章节片段生成三个纯函数区域，并保持现有测试样例不变。
- `useAudiobookPlayer.ts`：优先把语言识别和音色选择纯函数移到独立文件，再考虑播放状态机拆分。
- Rust/Tauri：保持命令注册集中，但后续原生命令继续增长时，将插件初始化、命令列表和平台适配边界拆清楚。

## 第二批采纳方案

### 混音状态规则抽象

将 `useSoundMixer` 中与 React 生命周期无关的规则抽到 `soundMixerState`：

- 初始音量生成。
- 预设音量合并。
- 可恢复播放列表生成。
- 声音库变化后的播放列表、恢复列表和音量状态规范化。

这不是泛用工具箱，而是混音领域规则入口。`useSoundMixer` 继续负责播放器命令、副作用、错误处理和 React 状态同步。

### 听书语言与音色规则抽象

将 `useAudiobookPlayer` 中的语言识别和音色匹配抽到 `speechLanguage`：

- 按文本内容识别 `zh-CN`、`en-US`、`ja-JP`、`ko-KR`。
- 将中文常见语言标签归一为同一语系。
- 按朗读语言选择默认匹配音色。

该模块可被未来导入预处理、段落预览或平台 TTS 适配复用，不绑定 React hook。

### EPUB 导入解析边界抽象

将 `epubImport` 拆成清晰的导入流水线：

- `epubXml`：XML/HTML 解析、命名空间无关的元素查询、ZIP 内路径解析。
- `epubPackage`：读取 `container.xml` 和 OPF package 中的标题、manifest、spine。
- `epubTextExtraction`：从 XHTML/HTML 文档提取可朗读标题和正文，过滤脚本、样式、导航等不可朗读内容。
- `epubSegments`：按 spine 阅读顺序读取章节并生成 `AudiobookSegment`。
- `epubImport`：只负责文件类型判断、ZIP 生命周期和顶层组装。

这组抽象对应 EPUB 导入的自然阶段，不引入与业务无关的通用解析框架。

## 不采纳方案

- 暂不做全仓目录重组。当前 `features` 边界仍然清楚，重组会增加大范围 diff 和回归风险。
- 暂不引入状态管理库。现有状态主要是局部 feature 状态，引入全局状态库不符合当前复杂度。
- 暂不拆声音目录数据文件。`soundCatalog.ts` 和 `soundPresets.ts` 行数较高，但大部分是声明式数据，拆分收益低于逻辑文件。
- 暂不把 `useSoundMixer` 改成 reducer。当前问题是领域规则散落，不是状态转移复杂到需要 reducer。

## 验收标准

- `AppWorkspace` 用户可见行为不变：三种模式可切换，声音、听书、听视频不会因模式切换互相停止。
- 全局定时停止仍会触发声音、听书和听视频停止。
- 注入测试播放器时不会创建真实运行时播放器。
- 修改后必须运行 `pnpm run check`；如果 `rtk` 不可用，需要明确说明已回退到原生命令。
